Resource-utilization features capture system- and device-level activity during module execution, including CPU/GPU utilization, memory utilization, clock frequencies, and memory use. Execution features capture the workload configuration and observed execution cost, including batch size, sequence length, FLOPs per token, execution time, NVML-reported GPU energy, and GPU count. We additionally include intra-module kernel overlap duration, measured as the time during which kernels belonging to the same module execute concurrently across GPU streams.
This feature allows the module-level regressor to capture energy variations associated with concurrent kernel execution. Model-structure features such as feed-forward dimension, Transformer-block count, hidden size, attention-head count, and key-value-head count expose architectural differences that determine tensor shapes and how work is divided across ranks. For communication modules, \sys{} records the amount of data transferred and the effective bandwidth of each inter-GPU event.

The feature representation is also designed to scale with GPU count. Instead of learning a separate set of coefficients for each physical GPU, \sys{} summarizes runtime features across participating GPUs using the mean, standard deviation, minimum, and maximum. The mean captures the overall activity level, while the spread and extrema expose imbalance and straggler behavior. These aggregates are combined with the static structural and communication features before training the module-specific regressors.

\subsection{Communication Energy Modeling}
\label{ss:design-communication}
To model the communication energy introduced by parallel inference, \sys{} first treats inter-GPU communication events as explicit modules in the model tree. 
For each communication event $e$, we trace the communication tensor sizes and calculate network transfer bytes sent ($B_{e}^{\mathrm{out}}$) and received ($B_{e}^{\mathrm{in}}$) by each GPU and use an offline-calibrated $\alpha$-$\beta$ model~\cite{hockney1988parallel2} to estimate the communication latency as:

\vspace{-2pt}
\begin{equation}
\label{eq:comm-latency-main}
T_{e}^{\mathrm{comm}} =
\alpha_{o,p} +
\beta_{o,p}
\left(
B_{e}^{\mathrm{out}} + B_{e}^{\mathrm{in}}
\right),
\vspace{-2pt}
\end{equation}

Here $o$ denotes the communication operation (e.g., AllReduce or point-to-point transfer), $p$ is the number of GPUs, $\alpha_{o,p}$ captures fixed startup and synchronization overhead, and $\beta_{o,p}$ captures the message-size-dependent transfer cost. For each event we define the per-GPU communication volume as $V_e=B_e^{\mathrm{out}}+B_e^{\mathrm{in}}$. We calibrate the model offline for every communication operation type and GPU count by sweeping communication volumes, recording the observed duration $T_e^{\mathrm{obs}}$, and fitting $T_e^{\mathrm{obs}}=\alpha_{o,p}+\beta_{o,p}V_e$. The corresponding effective bandwidth is $B^{\mathrm{eff}}_{o,p}=1/\beta_{o,p}$. This calibration is performed once per hardware/topology and is then reused by the predictor.

For ring AllReduce, the communication volume follows directly from the ReduceScatter and AllGather phases. If the communicated tensor has size $S_e$ bytes, each GPU sends and receives $(p-1)S_e/p$ bytes in each phase; therefore the total per-GPU communication volume is
\begin{equation}
V_e^{AR}=\frac{2(p-1)}{p}S_e.
\label{eq:allreduce_volume}
\end{equation}
For pipeline-parallel point-to-point transfers, the corresponding activation tensor size determines the event volume; for data-parallel AllGather, the final output tensor and number of replicas determine the volume. After predicting $T_e^{\mathrm{comm}}$, \sys{} converts communication time to energy using calibrated average communication power $\bar{P}^{\mathrm{comm}}_{o,p}$:
\begin{equation}
\widehat{E}^{comm}_e=\bar{P}^{comm}_{o,p}T_e^{comm}.
\label{eq:comm_energy}
\end{equation}
The resulting communication-module estimate is then composed with the compute-module estimates by the multi-level regressor in \S\ref{ss:design-prediction}.


\subsection{Measurement and Data Collection}
\label{ss:design-measurement}
%\aruna{can this be moved to after the regression discussion?}
\sys{} measures communication energy by first identifying the communication events introduced by each parallelism strategy and then isolating the corresponding windows in the execution trace. For instance, for tensor parallelism, these events relate to the AllReduce operation.
We align these communication windows with the system power trace and integrate power over the corresponding intervals to obtain communication-energy measurements for training the communication-module predictor. 
Effective bandwidth is computed from the observed communication volume and transfer time, and the bytes sent and received are derived directly from the tensor size being communicated.

\textbf{Tensor parallelism.} We repeatedly profile the ring AllReduce operation instead of relying on a single execution trace. Ranks do not always reach a collective at exactly the same time because of runtime scheduling, cache behavior, and memory-access variation. Consequently, the observed AllReduce interval contains both link activity and synchronization/waiting energy. We collect repeated runs to capture the distribution of leading and lagging GPU behavior across the ReduceScatter and AllGather phases, so that the communication predictor is not trained on one potentially unrepresentative synchronization instance.

\textbf{Pipeline parallelism.} Communication is isolated at every stage boundary. We use \texttt{nsys} timestamps to identify the completion of the last forward kernel on stage $i$ and the start of the first forward kernel on stage $i+1$. The interval between these events is attributed to the point-to-point activation transfer, and system power is integrated over the same interval to obtain the corresponding communication energy. This directly associates the transferred activation tensor with the energy consumed while moving it between the producing and consuming stages.

\textbf{Data parallelism.} Each replica completes its local forward pass independently and a final AllGather collates the outputs. We therefore profile the tail-end interval beginning when the output layer completes and ending when the AllGather finishes. Because there is one such output-collation event per inference request in our setup, this boundary is more straightforward than in tensor or pipeline parallelism and typically contributes less communication volume. Across all three strategies, bytes sent/received are derived from the communicated tensor size and communication pattern, while effective bandwidth is computed from observed transfer volume and duration.

For compute modules, \sys{} records (i) resource-specific signals that summarize system/GPU activity, and (ii) model-specific descriptors extracted from the LLM configuration.

\sys{} collects repeated offline measurements for each module across controlled execution runs to build a stable training dataset for the module-level regressors (explained in \S\ref{ss:design-prediction}). 
This strategy captures non-deterministic straggler effects in observed communication behavior of parallel deployments, and improves the stability of the learned regressors.
We note that \sys{} performs all measurements \emph{offline}. 
As a result, during inference, \sys{} incurs \be{no additional measurement overhead}.

\subsection{Multi-Level Regression}
\label{ss:design-prediction}
Our methodology for training regressors follows a hierarchical approach, training module-level predictors and then combining them for model-level prediction. 
As \sys{} obtains features from multiple GPUs, naively learning separate coefficients per GPU does not scale as the number of parameters grows with GPU count.
Instead, \sys{} computes and employs \emph{statistical aggregates} of the runtime features by computing the mean, standard deviation, min and max values across all GPUs. 
These are combined with the static structural features to form the complete feature vector for each sample.

\sys{} uses the following multi-level regression formulation: 
\vspace{-6pt}
\begin{equation}
\begin{aligned}
P_e(m) &=
\sum_{c \in \mathcal{C}(m)} \alpha(c)\,P_e(c),\\[2pt]
P_e(c) &=
f_{\mathrm{Module}(c)}\!\left(\mathrm{feat}(c)\right)
\quad \text{if } c \text{ is a compute module},\\[2pt]
P_e(c) &=
\bar{P}^{\mathrm{comm}}_{o(c),p}\,
T_{c}^{\mathrm{comm}}
\quad \text{if } c \text{ is a communication module},\\[3pt]
\alpha(c) &=
1 + \frac{\tanh(\mathbf{W}\,\mathrm{feat}(c)+b)}{\tau}.
\end{aligned}
\label{eqn:end2end-predicted-sum}
\vspace{-7pt}
\end{equation}

Eq.~(\ref{eqn:end2end-predicted-sum}) defines the final model-level prediction. 
Here, $P_e(m)$ denotes the predicted end-to-end energy of model $m$. 
$\mathcal{C}(m)$ is the set of compute and communication modules.

For a compute module $c$, $P_e(c)$ is predicted using the module-specific regression function $f_{\mathrm{Module}(c)}$, as a function of compute modules $\mathrm{Module}(c)$ and its features.
In our implementation, $f_{\mathrm{Module}(c)}$ is a decision-tree regressor trained separately for each module type.
For a communication module $c$, $P_e(c)$ is computed as the average observed communication power $\bar{P}^{\mathrm{comm}}_{o(c),p}$ multiplied by the communication time $T_{c}^{\mathrm{comm}}$ (obtained from Eq.~\eqref{eq:comm-latency-main}).
The average communication power is calibrated for the communication operation type $o(c)$ (e.g., AllReduce, AllGather) and the number of GPUs, $p$. 

Finally, $\alpha(c)$ is the learned composition weight for module $c$. 
This formulation makes the bottom-up prediction explicit: \sys{} first predicts the energy of compute and communication modules, then combines those module-level predictions to obtain the model-level energy $P_e(m)$.

This hierarchical composition enables \emph{cross-variant and cross-model reuse} since many modules (e.g., Attention and MLP blocks) are shared across different models. 
While we do not claim generalization to arbitrary architectures, our results in \S\ref{sec:model_prediction} demonstrate that \sys{} achieves  generalization across multiple model families.
